# BM25 实现与迁移

BM25 现在由 Milvus 2.5+ 的原生函数生成稀疏向量并评分。查询提交文本，不再将查询和文档两侧都乘 IDF，也不再读取或改写 `data/bm25_state.json`。稀疏索引使用 `BM25 / TAAT_NAIVE`，参数为 `k1=1.5, b=0.75`；该算法使用变化后的平均文档长度。Dense 仍使用 BGE-m3 + IP，融合仍使用 RRF。

本地预处理位于 `backend/bm25.py`：NFKC 归一化、小写化，保留数字、版本号、`GPT-4`、`C++`、`C#` 等标识符；中文使用连续 1/2/3 字符特征，不是词典分词。它能保留邻接信息，但会增加索引大小，仍需用真实问答集评估召回效果。服务端以 whitespace tokenizer 读取相同的 `lexical_text`。变更预处理规则需要升级 schema 标记并重建集合。

官方依据：[原生全文搜索与 BM25 索引参数](https://milvus.io/docs/v2.5.x/full-text-search.md)、[whitespace tokenizer](https://milvus.io/docs/v2.5.x/whitespace-tokenizer.md)。

## 已有集合升级

旧的 IP 稀疏向量不能直接用于新查询。代码会拒绝不匹配的 schema/索引，提示迁移；不会把格式不匹配悄悄当作 Dense 降级。上传、覆盖和删除也会在修改数据前检查集合格式。

1. 完成已有文档恢复任务，然后停止后端及其他会写这个集合的客户端。迁移使用后端同一进程锁，并检查未完成的事务日志；不要删除锁文件。
2. 启动部署所用的 Milvus（项目 compose 为 2.5.14），在 `SuperMew` 目录执行：

   ```powershell
   .venv/Scripts/python.exe scripts/migrate_bm25.py --target embeddings_native_bm25_v2 --activate
   ```

3. 脚本通过强一致游标复制已有文本、Dense 向量和元数据（包含动态字段），生成新的 lexical_text，无须重新调用嵌入模型。它逐行核对新集合内容，并再次检查源集合是否发生变化。核对成功后 `--activate` 才会备份并原子更新 `.env` 的 `MILVUS_COLLECTION`。
4. 重启后端。若部署通过系统环境变量或容器注入 `MILVUS_COLLECTION`，同时更新该配置，因为它优先于 `.env`。用已知文档查询、上传和删除进行实际验收。

可省略 `--activate` 只构建并核对新集合，然后手动切换部署配置；`--source` 可显式指定旧集合，`--env-file` 可指定配置文件。源集合必须包含当前应用需要的层级元数据。摘要核对在内存中保存每个不同分块的 SHA256 计数，内存随分块数量增长。

**失败行为：**任何复制、验证或配置切换失败均保留源集合；已经创建的目标集合也保留供检查。重试须选择另一个新集合名，脚本不会覆盖或删除集合，不会重放结果不明的 auto-id 插入。旧集合只代表迁移时的数据；新集合开始接收写入后，不能简单切回旧集合，否则看不到新写入。

## 上传、删除及恢复

上传写入 Dense 向量、原文、lexical_text 和元数据，Milvus 自动生成 sparse_embedding。删除由 Milvus 同步管理 BM25 数据；本地不再增减 N/df/avgdl。新事务快照保留 Dense 和 lexical_text，失败恢复时重新插入，由原生函数生成稀疏向量。旧事务仍支持原来的稀疏向量和本地状态恢复，但必须在原集合上完成后再迁移。

本地旧 BM25 文件可留存。它不再影响原生查询；旧单条稀疏查询编码 API 已明确停用。批量旧编码接口仅保留供旧格式适配器及恢复兼容使用。
